# CodePulse v1.5.0 — Concurrent Sessions & Thread-Native Tracking

**Status:** Accepted normative specification
**Target:** v1.5.0
**Implementation state:** Planned; this document does not claim that the
feature is implemented in the current 1.4-era release.

This document is the product and technical contract for the later v1.5
implementation. “Must” and “must not” are release requirements. An
implementation may choose different internal types or file layout when the
observable invariants in this document remain true.

The terms used throughout are deliberate:

- A **Workspace** is an organizational and navigation scope containing
  Projects.
- A **Project** is the canonical ownership boundary resolved from a configured
  folder.
- A **CodePulse Session** is one independently persisted work timeline with a
  stable UUID.
- A **Developer-Tool Thread** is one external Codex or OpenCode lifecycle,
  identified at runtime by `(DeveloperTool, externalSessionID)`.
- **Active Time** is wall-clock time covered by the union of active intervals.
- **Session Activity** is the sum of each session’s individual active
  duration.

## A. Milestone purpose

CodePulse now supports Multi-Project Workspaces, but its session architecture
still assumes one globally active session. That assumption prevents the app
from faithfully representing the way developers work when several tools or
threads are open at once.

v1.5 introduces first-class concurrent CodePulse Sessions. It must be possible
to independently track:

- multiple Codex threads in the same Project;
- Codex and OpenCode simultaneously;
- threads in different Projects;
- threads across different Workspaces; and
- manual and automated Sessions at the same time.

The feature is about independent Session identity and lifecycle. Merely
displaying multiple Developer-Tool contexts inside one timer is not
concurrency and does not satisfy this specification.

The existing product principles remain unchanged: native macOS, local-first,
no accounts, no cloud dependency, no telemetry or product analytics,
deterministic local Insights, no productivity scoring, and privacy-conscious
metadata-only Developer-Tool integrations.

## B. Core invariants

1. CodePulse may contain zero or more active Sessions. A persisted active
   collection contains only `running`, `paused`, or `finishing` Sessions; an
   `idle` Session is not persisted.
2. Every active Session has its own stable UUID. The UUID survives relaunch,
   migration, backup/restore, finishing, and conversion to completed History.
3. An automated Developer-Tool Thread is uniquely identified by
   `(DeveloperTool, externalSessionID)`. The external ID is an opaque,
   normalized integration value; it is not a Project ID and is not interpreted
   as a path or command.
4. Project identity must never substitute for Developer-Tool Thread identity.
   A Project may be shared by many Sessions, and a Thread may not be inferred
   from a Project name or Workspace selection.
5. One Developer-Tool Thread may own at most one active automated CodePulse
   Session at a time.
6. Multiple active Sessions may reference the same Project.
7. Multiple active Sessions may reference Projects in different Workspaces.
8. Pause, resume, finish, outcome editing, save, and discard always operate on
   one explicitly resolved Session.
9. Mutating one Session must not alter another Session’s lifecycle, timeline,
   automation claims, outcome, or persistence status.
10. Finishing or Git-capturing one Session must not globally block unrelated
    Sessions. A user may continue or finish another Session while the first
    one is collecting Git context.
11. Workspace selection is presentation/navigation state only.
12. Changing Workspace selection must never determine which already-running
    Sessions remain active, visible to lifecycle processing, or eligible for
    event routing.
13. Duplicate or ambiguous ownership must fail closed. The implementation must
    reject the event or command and leave existing Sessions unchanged rather
    than guessing.
14. Concurrent active-session state is bounded. v1.5 sets a maximum of **16
    active Sessions** (running, paused, or finishing, counted together). A
    start or event that would exceed 16 is rejected without evicting, merging,
    or silently finishing an existing Session. The bound applies after every
    migration, restore, and durable commit.

The 16-session bound is intentionally a small, deterministic guard consistent
with CodePulse’s existing bounded inbox, event, context, and control ledgers.
It is a safety limit, not a promise that 16 concurrent timers are a preferred
workflow.

## C. Persistence architecture

### Canonical state

The canonical persisted shape moves from one optional value:

```text
activeSession: ActiveSession?
```

to a collection:

```text
activeSessions: [ActiveSession]
```

The state schema advances from **2 to 3**. The schema-3 field is the sole
authoritative active-session collection. New code must not maintain a second,
authoritative “current session” field. A UI may hold a selected Session ID as
ephemeral presentation state, but that selection is never session ownership.

Each element preserves the existing `ActiveSession` semantics: UUID, Project
ID, Project-name snapshot, type, goal, start/end timestamps, phase, pause
intervals, outcome, Git context, GitHub context, Developer-Tool contexts, and
automation metadata including rule/source, claims, deadlines, and pending
automatic-save state.

### Migration rules

Migrations are forward-only, lossless for valid data, and non-destructive. A
candidate state is decoded, normalized, integrity-validated, atomically
written, and read back before it becomes live. A failed migration leaves the
original bytes and in-memory state available for recovery.

- **Schema 1 to schema 3:** apply the existing legacy-to-workspace migration
  first (including creation of one default Workspace and assignment of legacy
  Projects), then map the legacy optional `activeSession` to
  `activeSessions`. A missing legacy value becomes `[]`; a present valid value
  becomes a one-element array. Preserve every Session field listed above,
  including its UUID and automation metadata. The resulting state has schema
  version 3 and canonical workspace/project relationships.
- **Schema 2 with no active Session:** decode `activeSession == nil` as
  `activeSessions == []`.
- **Schema 2 with one active Session:** decode the value as exactly one
  element in `activeSessions`, preserving its UUID, project and name snapshot,
  type, goal, timestamps, phase, pauses, outcome, Git/GitHub context,
  Developer-Tool contexts, and automation metadata byte-for-byte where the
  decoder permits. No new UUID may be generated for this migration.
- **Schema 3:** decode `activeSessions` as the canonical collection. A schema-3
  document that has only the old `activeSession` field, both fields, or an
  otherwise ambiguous active representation is invalid; the migration must
  not choose one field silently.

An implementation may retain decode-only compatibility code for old keys, but
every successful write after migration must emit schema 3 with
`activeSessions`, not the legacy key.

### Integrity validation

The state validator must reject, before publication or restore:

- duplicate active-session UUIDs;
- an active UUID that also appears in completed History;
- duplicate automated Developer-Tool Thread ownership keys across active
  Sessions (including `startedBySource` and active Developer-Tool claims);
- an active Session whose non-nil Project ID does not exist, points to a
  missing Workspace, or violates the canonical Project/Workspace relationship;
- an active Session referring to an archived Project (active Sessions must
  reference an existing, non-archived Project when `projectID` is non-nil);
- invalid phase/timestamp/pause timelines, including more than one open pause
  interval or an open interval in a running/finishing Session;
- an active-session collection larger than 16; and
- malformed IDs, invalid Developer-Tool ownership metadata, or other
  corruption that would make routing ambiguous.

Project-name snapshots remain historical display data and do not repair a
missing Project ID. A Project that is moved between Workspaces retains its ID;
the Session’s Workspace is always derived from that Project relationship.
Validation must not “repair” a dangling relationship by using the selected
Workspace or a matching name.

## D. Developer-Tool Thread identity and routing

For automated Codex/OpenCode tracking, the runtime ownership identity is:

```text
(tool, externalSessionID)
```

The canonical working directory is still required to resolve the Project. The
existing path matcher remains the ownership boundary: canonicalize and validate
the event path, consider eligible active Projects whose configured folder
contains it, choose the most specific unique Project root, and fail closed for
duplicate roots or no match. Workspace selection and the frontmost application
never participate in that ownership decision.

For every validated event, process this routing contract in order. Thread
identity determines which active Session may own the event; canonical working-
directory resolution determines whether the event is authorized for that
Session’s Project. Neither may substitute for the other:

1. Canonicalize and validate the event working directory. Reject the event if
   it is unsafe, non-canonical, or otherwise invalid.
2. Resolve that canonical directory to exactly one eligible active Project
   using the deterministic Project path resolver above. Reject the event if
   there is no unique eligible Project.
3. Resolve the active automated Session, if any, owned by the event’s
   `(tool, externalSessionID)`.
4. If a Thread-owned Session exists, require
   `resolvedProjectID == session.projectID` and require that the Session is
   otherwise eligible for the event timeline (including phase and timestamp
   boundaries). Only after both checks pass may CodePulse mutate or enrich that
   Session.
5. If the Thread owner exists but the event resolves to a different Project,
   fail closed. Do not move or rebind the existing Session, attach the event to
   another Session, or create a second owner for the same Thread identity.
6. If no active Thread owner exists, consult the bounded retired-Thread ledger,
   then apply normal Developer-Tool rule resolution for the resolved Project
   and tool. If the rule claims the event, perform the admission/reservation
   sequence below. If the 16-session limit permits it and the reservation
   succeeds, create one new active automated Session owned by that Thread.
7. If automation does not claim the event, context-only enrichment may attach
   to a manually started Session only when the target is unambiguous. The target
   must have the resolved Project and a timeline containing the event timestamp.
   If more than one manual Session is equally valid, leave all Sessions
   unchanged and acknowledge/reject the event according to the existing bounded
   inbox protocol.

An existing Thread owner is never allowed to bypass Project revalidation. For
example:

```text
Existing:   (Codex, abc123) -> CodePulse
New event:  (Codex, abc123), cwd -> ProxPilot
Result:     reject/fail closed; the CodePulse Session remains unchanged and no
            ProxPilot owner is created for abc123
```

A same-Project event must never attach to an automated Session owned by a
different external Thread merely because the Project matches.

The following edge cases are normative:

- **Same external ID from different tools:** `(Codex, X)` and `(OpenCode, X)`
  are distinct Thread identities and may own separate Sessions.
- **Duplicate or replayed events:** the validated event UUID ledger remains
  authoritative for replay prevention. Replaying the same event ID is a
  no-op. A new event ID for the same active Thread updates its existing owner
  only after the working-directory Project revalidation above; it does not
  create another Session.
- **Stale events:** events outside the integration age/future-skew limits,
  events earlier than the owner’s start boundary, or events that arrive after
  a completed or discarded owner are not allowed to create or mutate a Session.
  The retired-Thread ledger below applies even when a delayed event has a new
  event UUID. A stale session-ended event may be acknowledged without changing
  a newer Session for the same Project.
- **Session-ended events:** an ended event marks only the matching Thread’s
  context/claim as ended and starts that Session’s configured pause/finish
  countdown. It does not synchronously finish every Session in the Project.
- **Malformed or unknown Project paths:** invalid, non-canonical, unknown, or
  unsafe paths are rejected and cannot create a Session. No selected Workspace
  fallback is permitted.
- **Inactive or archived Projects:** they are not eligible for new automated
  ownership or context attachment. Existing historical context remains
  readable; it is not revived by a late event.

The event-processing transaction must persist Session mutation and event
acknowledgement together. If persistence fails, the event remains retryable
and no other Session is changed.

### Retired Developer-Tool Thread ownership

When an automated Developer-Tool Session is finally completed or discarded,
each distinct automated ownership key associated with it enters a bounded,
machine-local retired-Thread ledger. A reservation for each such key was made
before admission and remains held for the Session's active lifetime. An entry
is metadata-only and is conceptually:

```text
RetiredDeveloperToolThread
  tool
  externalSessionID
  retiredAt
  lastAcceptedEventAt
```

`lastAcceptedEventAt` is the latest event timestamp accepted for that owner
before retirement; it is routing metadata only.

The effective retired-Thread protection capacity is **2,048 Thread identities**
shared by protected retired identities and active Developer-Tool ownership keys
whose retirement protection is reserved. The invariant is:

```text
protectedRetiredThreadCount
+ activeDeveloperToolOwnedThreadCount
<= 2048
```

Each active automated Developer-Tool Thread identified by
`(DeveloperTool, externalSessionID)` consumes one reserved future
retirement-protection slot while it remains active. When that Thread completes
or is discarded, its reserved slot becomes its protected retired-Thread
tombstone. When the tombstone expires after the **7-day (168-hour)** protection
window, that capacity becomes available again. Reservations are counted per
distinct Thread identity, not merely per Session UUID; if the valid model ever
contains multiple distinct ownership keys in one automated Session, each key
has its own reservation. The expected normal case remains one automated Thread
owner per Developer-Tool Session. Manual Sessions with no automated
Developer-Tool ownership, the single application-trigger-owned automated
Session unless it also independently has Developer-Tool ownership, and
completed History without a currently protected retired identity do not consume
this capacity.

Before CodePulse creates a new automated Developer-Tool-owned Session, it must
perform these steps in order:

1. Prune expired retired-Thread entries first.
2. Count all remaining protected retired Thread identities.
3. Count all currently active Developer-Tool ownership keys that will require
   a retirement tombstone, counting each distinct `(DeveloperTool,
   externalSessionID)` identity once.
4. Determine whether admitting the new owner would make
   `protectedRetiredThreadCount + activeDeveloperToolOwnedThreadCount + 1`
   exceed 2,048. If it would, reject the new automated Developer-Tool Session
   start before admission. Do not evict a protected tombstone, exceed the
   bound, mutate unrelated Sessions, or create the Session first; the triggering
   event remains safely rejected or acknowledged according to the existing
   inbox/event protocol.
5. If the bound permits admission, reserve the new owner's slot before
   publishing the new active Session.

A matching `(tool, externalSessionID)` in the retired ledger remains protected
for **7 days (168 hours) after `retiredAt`**, equal to the maximum accepted
Developer-Tool event age. While protected, an event with that Thread identity
must not create a replacement Session, even when it carries a new event UUID;
it is rejected or acknowledged without changing unrelated Sessions. The same
event UUID remains governed by the separate processed-event ledger, which solves
duplicate delivery rather than retired-Thread resurrection.

The reservation guarantees that every already-admitted automated
Developer-Tool Session can later finish, save, or be discarded normally. When
ownership ends, CodePulse converts each reserved key into its corresponding
protected retired-Thread record. Retirement always succeeds with respect to
capacity, even when the retired-entry portion has no free slot; it must never
silently discard the protection record or evict another still-protected Thread
identity. Capacity exhaustion is handled only when admitting a new owner.

The retired-Thread ledger and active reservations are persisted in machine-local
AppState processing metadata so relaunch cannot reopen the resurrection window
or lose a reservation. Expired entries are pruned first on every insertion or
maintenance pass. When multiple expired entries are processed, use deterministic
oldest order `(retiredAt, lastAcceptedEventAt, tool, externalSessionID)`; no
still-protected entry may be pruned or evicted. Because admission reserves
capacity, an admitted owner's retirement conversion cannot exceed the bound.

This ledger is not user-authored history, a transcript, or a Developer-Tool
content store. Portable backups omit/reset it, just like the processed-event
and control ledgers. Restore resets the local tombstones and must not treat them
as historical user data; imported active Session UUIDs and timelines remain
subject to normal validation.

## E. Automation lifecycle

Automation state and deadlines belong independently to each active Session.
Claims, pause deadlines, finish deadlines, minimum-save duration, pending automatic
save, and relinquishment are all keyed by that Session’s UUID.

Required behavior includes:

- Activity from Thread B resets or resumes only Session B. Thread A’s
  inactivity countdown continues from its own last matching signal.
- Ending Thread A changes only A’s claim/context and A’s automatic lifecycle;
  Thread B continues unchanged.
- Automatic pause and finish deadlines are evaluated independently for every
  active Session. A paused Session may finish while another Session remains
  running.
- Automatic save applies only to the owning Session. A minimum-duration discard
  or save decision for A cannot discard, finish, or rewrite B.
- Disabling or reconfiguring automation relinquishes control only for Sessions
  whose supporting rule/claim is no longer valid. Other valid automated
  Sessions retain their claims. Imported automation claims remain disabled
  until the existing restore review flow permits local re-enablement.
- Manual lifecycle actions on a Session relinquish automation control for that
  Session only. They do not take control of, pause, or finish another
  automated Session.

### Application automation scope boundary

v1.5 permits **at most one active/finishing application-trigger-owned automated
Session at a time**. That one application-owned Session may coexist with manual
Sessions,
Codex Sessions, OpenCode Sessions, and other Developer-Tool Sessions, and it
counts toward the global 16 active/finishing Session limit. Developer-Tool
concurrency must never be suppressed merely because the application-owned
Session exists.

Application-trigger matching and deactivation affect only the application-owned
Session. A second simultaneous matching application trigger must not create a
second application-owned Session under v1.5; the existing one remains the sole
application-owned owner and unrelated Sessions remain unchanged. This is a
deliberately frozen boundary, not a complete redesign, and a later milestone
may revisit application-trigger concurrency. Application triggers must not
expand into process/window spying or establish Thread identity.

## F. Manual Sessions

Multiple concurrent manual Sessions are part of the correct domain model.
Manual and automated Sessions may coexist, including in the same Project.

A manually started Session has no automation lifecycle owner. Automation may
enrich it with Developer-Tool context only through the unambiguous routing
rule in Section D; it must not claim pause, resume, finish, or automatic-save
authority over that manual Session. If two manual Sessions are equally valid
targets, enrichment fails closed.

Manual start must honor the 16-session bound and an active Project’s existing
eligibility rules. Starting another manual Session must not implicitly pause,
finish, or change the selected Workspace or any existing Session.

## G. SessionStore and lifecycle API direction

The lifecycle API becomes Session-ID-targeted. Conceptually, the later
implementation exposes behavior equivalent to:

- start returns or exposes the created Session UUID;
- `pause(sessionID:)` targets one Session;
- `resume(sessionID:)` targets one Session;
- `finish(sessionID:)` targets one Session;
- outcome editing targets one Session ID in the in-app SessionStore/UI;
- save targets one finishing Session ID in the in-app SessionStore/UI; and
- discard targets one finishing Session ID in the in-app SessionStore/UI.

Names and Swift overload details may vary, but an operation must resolve a
single UUID before mutating state. A selected Session in a view is not a
global current Session.

Outcome editing, save, and discard are internal SessionStore/UI lifecycle
operations. They are not new `codepulsectl` verbs in v1.5.

Existing no-ID convenience paths may remain for compatibility only when there
is exactly one eligible Session for that operation. When zero Sessions are
eligible, preserve the existing invalid-transition behavior. When multiple
Sessions are eligible, reject as ambiguous and require a Session ID. Never
pick the newest, oldest, selected-Workspace, or frontmost-tool Session as an
implicit default.

Every lifecycle mutation remains durably committed before it is published in
memory. A failed commit leaves the targeted Session and every unrelated
Session unchanged, with the existing retry/recovery guarantees intact.

## H. Git and GitHub concurrency

The current global Git-capture flag and single capture ID cannot remain
authoritative in v1.5. Git capture state must be tracked per Session UUID,
with independent jobs/statuses such as `scheduled`, `running`, `succeeded`,
`failed`, or `ambiguous`. At most one capture job may mutate a given Session’s
Git context at a time, but captures for different Sessions may run together.

One Session’s Git capture must not block another Session’s:

- lifecycle transition;
- finish or outcome editing;
- save or automatic save (except while that same Session’s required capture is
  pending);
- Git/GitHub enrichment; or
- relaunch recovery.

If A’s capture fails or persistence of A’s enrichment fails, B remains
available and unchanged. Restore is the explicit exception: restore is blocked
while any active/finishing Session has a relevant per-Session capture in
progress (see Section M).

### Discovery and repository boundaries

For an automatically created Developer-Tool Session, Git discovery should
start from the triggering event’s canonical working directory when that is
available. It must not assume the configured Project root is the exact
repository/worktree boundary. The discovery algorithm must safely handle:

- concurrent Git worktrees with different roots or branches;
- nested repositories, choosing and recording the repository that contains
  the triggering directory according to the implementation’s documented
  deterministic rule;
- detached HEAD and branch changes; and
- a repository that disappears or becomes unreadable during capture.

Repository identity, canonical repository root, branch/HEAD snapshots, and
valid GitHub repository or pull-request context may still be retained per
Session. Git/GitHub operations remain read-only and failure-tolerant.

### Git observation windows and same-repository ambiguity

Git mutation deltas are derived from repository-wide snapshots, so visible
Session timer overlap is not the ambiguity predicate. For each Session and
canonical repository identity/root, record a **Git observation window**:

- it begins at the successful start-snapshot boundary, not at `startedAt`; if
  the start capture is delayed, the actual successful snapshot boundary is the
  start of the window;
- it ends at the successful final-snapshot boundary; if final capture completes
  after the Session timer finishes, the window continues until that actual
  repository observation; and
- while final capture has not succeeded, the window remains open/unknown rather
  than ending at the Session timer. A missing or failed required boundary cannot
  establish exact non-overlap.

For two Sessions, numeric mutation deltas are ambiguous when both resolve to
the same canonical repository identity/root and their Git observation windows
overlap in a way that could include the same repository-wide mutation in both
observations or leave attribution unattributable. Treat intervals as
overlapping when their recorded boundaries intersect; if exact non-overlap
cannot be established because a boundary is delayed, missing, failed, or
unknown, treat the affected same-repository Sessions as ambiguous
conservatively. Distinct canonical repository roots/worktrees are not the same
repository for this predicate, even when they share an upstream GitHub URL.

For example, if Session A’s timer finishes at 10:00 but its final Git snapshot
does not complete until 10:02, and Session B starts/modifies the same canonical
repository at 10:01, A’s window overlaps B’s activity/capture window. A’s
repository mutation delta is not uniquely attributable even though the visible
Session timers do not overlap.

When ambiguity exists, **suppress numeric per-Session mutation deltas for all
affected Sessions**: `commitCount`, `filesChanged`, `insertions`, and
`deletions` must be absent or excluded from attributable totals. The follow-up
commit’s policy is suppression, not a confidently attributable value with only
a warning. An implementation may retain the repository-wide observation or
expose an explicit `ambiguous`/`non-attributable` status. Repository identity,
branch, HEAD, GitHub repository, and PR context may remain when independently
valid.

## I. Menu-bar UX contract

### Zero active Sessions

Preserve normal idle behavior: the user can choose Workspace, Project, type,
goal, or preset and start a manual Session. No active-session hub is shown.

### Exactly one active Session

Preserve the familiar 1.4 detail/control experience as closely as practical:
show the Project/name snapshot, type, goal, timer, pause/resume, finish, and
available context. Controls resolve to the sole Session ID even if the UI
does not display that implementation detail.

### Multiple active Sessions

Show an **Active Sessions** hub. It must:

- list every active and finishing Session, including paused Sessions;
- make every Session discoverable without relying on a “current” implicit
  choice;
- group by Workspace and/or Project where that improves scanability;
- show Developer Tool where applicable;
- show Session type;
- show running, paused, or finishing state;
- show elapsed active duration for each Session;
- let the user select a Session to open that Session’s detail and controls;
- scope finishing and outcome UI to the selected Session;
- provide a path to start another manual Session; and
- avoid implying that one Session is globally current.

The status-bar title must not become a concatenation of individual timers. A
compact aggregate such as “3 sessions” is appropriate. Accessibility output
must state aggregate active/running/paused/finishing counts and expose each
selectable Session individually with its Project (or No Project), Workspace
when useful, tool, type, state, and elapsed duration.

Git-capture progress, save availability, lifecycle errors, and retry actions
shown in the hub or detail must identify the affected Session. A capture in A
must not disable B’s controls.

## J. Workspace behavior

Workspace switching is allowed while any Sessions are active, paused, or
finishing. Workspace selection controls:

- navigation;
- Project selection for the next manual start;
- default context for new manual work; and
- Workspace Dashboard scope.

Workspace selection does **not** pause Sessions, hide Sessions from lifecycle
processing, finish Sessions, transfer ownership, or affect Developer-Tool
routing. A Session remains associated with its Project; its Workspace is
derived through `Session.projectID -> ProjectRecord.workspaceID`.

Project move and archive operations are blocked whenever **any** active or
finishing Session references that Project, including a paused Session. The
operation must identify the blocking Session(s) if the UI can do so. Completed
History does not by itself prevent a move or archive.

## K. Insights and concurrency semantics

v1.5 must expose two distinct time concepts whenever concurrency can make
their values differ.

### Active Time

Active Time is human-facing wall-clock active time. For a selected timeframe,
Project/Workspace scope, and reference date:

1. derive each Session’s active intervals after clipping to the timeframe and
   removing pauses;
2. take the union of all those intervals; and
3. sum the duration of the union.

Example:

```text
Session A: 10:00–11:00
Session B: 10:30–11:30
Active Time: 1h 30m
Session Activity: 2h
```

Active Time must never exceed the wall-clock span covered by the selected
interval. Overlap is counted once in this metric.

### Session Activity

Session Activity is the sum of each Session’s individual active duration after
the same clipping and pause rules. It answers “how much Session work was
recorded?” and may exceed Active Time when Sessions overlap. Session counts,
average Session duration, longest Session duration, and Project/type duration
breakdowns are based on individual Sessions and must not be mislabeled as
wall-clock Active Time.

The UI and export/report model must either expose both values or clearly label
which one is being shown. A single legacy `totalDuration` value must not hide
the distinction in a concurrent result.

### Aggregation rules

- **Daily aggregation:** clip active intervals to each local-calendar-day
  boundary before taking the union for daily Active Time. Sum individual
  clipped durations for daily Session Activity. A session crossing midnight
  contributes only its interval on each day.
- **Project/type breakdown:** report Session Activity by Project and type,
  because one instant may legitimately belong to multiple simultaneous
  Sessions. Label these values as Session Activity; do not present their sum
  as a decomposition of overall Active Time. If a wall-clock allocation is
  added later, it must use a documented deterministic attribution rule and
  must preserve the overall union total.
- **Peak concurrency:** an optional peak concurrent-session count is allowed
  and should be derived from the maximum number of active intervals covering
  one instant. It is a descriptive metric, not a score.
- **Digests:** daily/weekly digest Active Time uses the interval union;
  Session count and top Project/type use Session Activity inputs. When overlap
  is present, include both labeled values (or an explicit overlap indicator)
  so a digest cannot imply that summed activity is wall-clock time.
- **Workspace Dashboard:** within the selected Workspace’s Project set, show
  active-session count and wall-clock Active Time from the union. Show
  Project/type activity as labeled Session Activity. Active Sessions in other
  Workspaces remain active and are not paused or hidden from lifecycle
  processing.
- **Comparison periods:** apply the same metric definitions independently to
  the primary and comparison interval. Do not compare Active Time in one
  period with Session Activity in another.

### Focus Patterns

Focus Patterns remain observable timing summaries, not productivity or
cognition judgments. They must become overlap-aware:

- sustained-focus duration is derived from union coverage of active segments,
  not by adding overlapping Session durations;
- sustained-focus share is `sustained union duration / Active Time`, clamped to
  the mathematical range 0–100%, and cannot exceed 100%;
- an overlap of Project A and Project B is represented as concurrent coverage,
  not as a fabricated A-then-B sequential switch; and
- project-switch counts may be incremented only when one Project’s final active
  segment ends and a different Project’s first active segment begins without
  overlap and within the existing interruption-grace rule. Starting a second
  overlapping Project counts as concurrent coverage, not a switch; the
  implementation must not invent an ordering from UUID or menu selection.

Focus blocks may retain the contributing Session/Project annotations for
inspection, but their duration is the union duration. Hour/day buckets use
that same non-overlapping coverage.

## L. `codepulsectl` and local control

The planned v1.5 `codepulsectl` surface remains limited to existing control
capabilities:

```text
codepulsectl status
codepulsectl status --json
codepulsectl start --preset "Preset Name"
codepulsectl start --project "Project Name" --type coding [--goal "..."]
codepulsectl pause --session-id <uuid>
codepulsectl resume --session-id <uuid>
codepulsectl finish --session-id <uuid>
```

The exact option spelling may vary, but every v1.5 lifecycle mutation must
carry or resolve one UUID before mutation. A successful start must expose the
created Session UUID in machine-readable output and, where appropriate, in
human-readable output. Save, discard, and outcome editing remain
Session-ID-targeted in the in-app SessionStore/UI; v1.5 does not add them as
`codepulsectl` commands.

Compatibility behavior for existing no-ID `pause`, `resume`, and `finish`
mutations is strict:

- zero applicable Sessions retain the existing invalid-transition behavior;
- exactly one applicable Session permits a no-ID command for compatibility;
- multiple applicable Sessions make a no-ID command ambiguous and require
  `--session-id`; and
- no command may select a Session arbitrarily by recency, Workspace, Project,
  tool, or frontmost application.

`status` and `status --json` must represent all active/finishing Sessions,
including IDs, Project/name snapshot, Workspace when resolvable, type, phase,
elapsed duration, Developer Tool/automation indicator, and per-Session Git
capture status where relevant. The status shape must distinguish zero,
one, and many Sessions.

Adding `sessionID`, an active-session array, and per-session capture/status
fields is a control protocol change. The implementation must publish an
explicit control command/status/response schema version (planned v2), accept
legacy v1 decoding only under the compatibility rules above, reject unknown
or ambiguous fields, and never reinterpret a v1 no-ID command as a random
Session mutation.

## M. Backup and restore

The portable backup format advances to **version 3**. It contains schema-3
state with `activeSessions`, and its preview exposes `activeSessionCount` (not
only a boolean). A compatibility view may derive a boolean for old callers,
but the v3 contract is count-based.

The importer must support:

- backup v1: reject workspace-era metadata, migrate legacy Projects into one
  default Workspace, and map an optional active Session to a one-element
  `activeSessions` array;
- backup v2: decode schema-2 Workspace state and map its optional
  `activeSession` to zero or one `activeSessions` element; and
- backup v3: decode the canonical schema-3 `activeSessions` collection.

Backup validation must check:

- unique active IDs;
- no active ID collision with completed-session IDs;
- unique automated Developer-Tool Thread ownership;
- valid Project/Workspace references;
- valid Session and pause timelines;
- the 16-session active bound; and
- the existing backup envelope, size, path, and configuration constraints.

Restore remains transactional. It is blocked while any active or finishing
Session exists, or while any relevant per-Session Git capture is in progress.
The current pre-restore recovery backup, atomic candidate write/readback,
post-replacement verification, rollback attempt, unreadable-state preservation,
ledger reset, and recovery-window guarantees remain in force. Restore replaces
the local state; it does not merge concurrent Sessions.

Imported active timelines and captured contexts are preserved, while machine-
local replay ledgers and automation claims are normalized according to the
existing restore safety rules. A restored Session’s UUID and history identity
must not be regenerated.

## N. Privacy contract

Concurrent tracking remains local and metadata-only. Multiple local active
Sessions do not expand what CodePulse collects or authorize cloud processing.

CodePulse may retain bounded metadata for each simultaneous local Thread,
including:

- Developer Tool name;
- external Session ID used for lifecycle routing;
- validated event type and timestamps;
- canonical working-directory metadata used for Project resolution; and
- model/profile labels when supplied reliably by the integration.

CodePulse continues not to collect Developer-Tool prompts, messages,
responses, transcripts, command text, command output, tool-call arguments or
results, source-code contents, secrets/keys, permission decisions, reasoning,
conversation summaries, arbitrary window contents, keystrokes, or screen
contents. Multiple concurrent Sessions do not authorize a broader inbox or
filesystem scan.

The existing bounded event/context ledgers, local-only backup behavior, and
no-cloud/no-account/no-telemetry product contract remain unchanged. Any
developer metadata in a backup is still user-controlled local data and may be
sensitive; it is not transmitted by concurrency itself.

## O. Security and trust boundaries

The v1.5 implementation must preserve and make explicit these boundaries:

- events enter only through validated local integration metadata and the
  existing CodePulse-owned inbox/atomic-file protections;
- Project ownership comes from canonical working-directory resolution against
  active configured Project folders;
- Thread ownership comes from `(tool, externalSessionID)`;
- selected Workspace and frontmost Developer-Tool application never establish
  Project ownership or Thread identity;
- duplicate Thread identities, duplicate active IDs, and ambiguous manual
  targets fail closed;
- malformed, replayed, stale, or unsupported events cannot create unbounded
  Sessions;
- the 16 active-session bound is enforced before durable publication and after
  decode, migration, backup import, and restore;
- restore validates identifiers, timelines, ownership, and Project/Workspace
  references before replacement;
- lifecycle and Git-capture mutation are scoped to a Session UUID, preventing
  global session bleed;
- concurrent Git captures use isolated per-Session state and cannot authorize
  writes to another Session or repository; and
- existing symlink/path, permissions, inbox, event-size, timestamp, and
  persistence transaction protections are not weakened to make concurrency
  convenient.

An event that cannot be attributed safely is less useful than an event that is
wrong. The implementation must prefer rejection, a bounded ambiguous marker,
or a retryable persistence failure over silently attaching data to a plausible
Project or Session.

## P. Release-blocking acceptance matrix

The following cases are release-blocking. Each test must assert the targeted
Session IDs and the unchanged state of every unrelated Session, not merely a
visible timer label.

| ID | Scenario | Required result |
| --- | --- | --- |
| 1 | Codex A and Codex B in the same Project | Two active Sessions with distinct UUIDs and distinct `(Codex, externalSessionID)` owners. |
| 2 | Codex and OpenCode in the same Project | Two independent Sessions; the different tools do not collide. |
| 3 | Same tool with different external IDs | Two independent Sessions. |
| 4 | Same external ID with different tools | Two independent Sessions because the tool is part of the key. |
| 5 | Threads in different Projects | Each event resolves to its own Project and Session. |
| 6 | Threads in different Workspaces | Both remain active; selected Workspace does not filter lifecycle processing. |
| 7 | Manual and automated Session | Both coexist; automation owns only the automated Session. |
| 8 | End Thread A while Thread B runs | A enters its configured lifecycle/finishing path; B’s phase, deadlines, and context are unchanged. |
| 9 | Activity on paused B | Only B resumes and receives the new activity; A remains paused or in its own phase. |
| 10 | Duplicate event ID | No duplicate Session, claim, context event count, or lifecycle transition. |
| 11 | Relaunch with multiple active Sessions | All valid Sessions restore with UUIDs, phases, pauses, claims, and contexts intact. |
| 12 | Multiple finishing Sessions | Each keeps an independent outcome editor, save/discard result, and completed ID. |
| 13 | Automatic save of A | A alone is saved/discarded; B remains active and intact. |

| 21 | Backup v2 with one active Session | Import/restore produces one-element `activeSessions` with no regenerated identity. |
| 22 | CLI lifecycle command without ID when ambiguous | Command is rejected with an ambiguity result and requires `--session-id`. |
| 23 | Two overlapping one-hour Sessions | Overall Active Time is 1h for complete overlap; Session Activity is 2h. |
| 24 | Concurrent Project overlap in Focus Patterns | No fake sequential Project switch; sustained-focus share is at most 100%. |
| 25 | Thread B event resolves to same Project as Thread A | Event attaches only to B’s owner (or creates B if eligible), never to A solely by Project match. |
| 26 | Malformed, unknown, unsafe, or inactive Project path | Event is rejected/cleaned up without creating or mutating a Session. |
| 27 | Stale event after a newer owner exists | Event cannot create a second owner or rewind the newer Session’s timeline. |

| 31 | Restore during any per-Session Git capture | Restore is rejected; no capture or state is partially discarded. |
| 32 | Active-session limit | The 17th eligible start/event is rejected, existing 16 Sessions remain unchanged, and state remains valid after relaunch. |
| 33 | Zero active Sessions in menu bar | Normal idle controls appear; no stale selected Session or timer remains. |
| 34 | Multiple active Sessions in menu bar/accessibility | Active Sessions hub lists every Session, aggregate counts are announced, and each Session has individually selectable controls. |
| 35 | Schema-1 legacy state with one active Session | Workspace and active-session migrations are both lossless and produce schema 3 without deleting legacy data. |
| 36 | Backup v1/v2/v3 preview | Preview reports the correct active-session count and validates IDs, timelines, ownership, and bounds before confirmation. |
| 37 | Existing Thread ID resolves to a different Project | `(tool, externalSessionID)` owner is rejected after Project revalidation; no rebinding, second owner, or mutation occurs, and every unrelated Session remains unchanged. |
| 38 | Late event with the same UUID after a completed Thread | The processed-event/retired-owner checks produce no mutation or resurrection; the completed owner and every unrelated Session remain unchanged. |
| 39 | Late event with a new UUID after a completed Thread | The protected retired-Thread entry rejects resurrection; no new Session or alternate Project owner is created, and unrelated Sessions remain unchanged. |
| 40 | Late event with the same UUID after automatic discard | No replacement active Session or duplicate history record is created; the discarded owner and unrelated Sessions remain unchanged. |
| 41 | Late event with a new UUID after automatic discard | Retired-Thread protection rejects the event even with a new UUID; no owner is recreated and unrelated Sessions remain unchanged. |
| 42 | Late event with the same UUID after manual discard of an automated Session | Duplicate/replay and retirement checks prevent resurrection; the discarded Session and unrelated Sessions remain unchanged. |
| 43 | Late event with a new UUID after manual discard of an automated Session | The retired-Thread tombstone rejects the event; no replacement owner is created and unrelated Sessions remain unchanged. |
| 44 | Relaunch while a Thread is retired | Persisted machine-local retirement metadata survives relaunch and continues rejecting delayed events; active and unrelated Sessions remain unchanged. |
| 45 | Reuse an expired retired Thread identity | Reuse is rejected until 7 days after `retiredAt`, then may create a genuinely new owner only after expiry and normal Project/rule checks; unrelated Sessions remain unchanged. |
| 46 | Same-repository visible Session timer overlap | Sessions sharing one canonical repository root have numeric commit/file/insertion/deletion deltas suppressed for all affected Sessions; repository identity metadata and unrelated Sessions remain unchanged. |
| 47 | Non-overlapping timers but overlapping Git observation windows | A delayed final capture (for example A finishes at 10:00, final snapshot at 10:02, B starts at 10:01) makes same-root deltas ambiguous and suppresses them for all affected Sessions; unrelated Sessions remain unchanged. |
| 48 | Same Project with separate Git worktrees/repository roots | Distinct canonical repository identities/roots do not trigger false ambiguity; independently valid numeric deltas remain attributable and unrelated Sessions remain unchanged. |
| 49 | Failed or missing same-repository capture boundary | Exact non-overlap cannot be proven, so affected same-root numeric deltas are conservatively suppressed; repository metadata and unrelated Sessions remain unchanged. |
| 50 | One application-owned Session plus several Developer-Tool Sessions | Exactly one application-trigger-owned Session coexists with multiple Codex/OpenCode and/or manual Sessions, all counted toward 16 and independently routable; unrelated Sessions remain unchanged. |
| 51 | Second simultaneous application-trigger match | v1.5 creates no second application-owned automated Session; the existing application owner and all Developer-Tool/manual Sessions remain unchanged. |
| 52 | Ambiguous CLI pause/resume/finish | A no-ID mutation with multiple eligible Sessions is rejected and requires `--session-id`; status still reports zero/one/many, and no save/discard/outcome CLI verbs are required or accepted. Unrelated Sessions remain unchanged. |
| 53 | Retired-thread capacity saturation | With all 2,048 protection slots consumed by any combination of protected retired Thread identities and reserved active Developer-Tool owners, an eligible new owner is rejected before its Session is admitted; no protected identity is evicted, existing active Sessions remain unchanged and can still finish/save/discard normally, the protected-plus-reserved count never exceeds 2,048, unrelated Sessions remain unchanged, and valid state survives relaunch. With exactly one slot available, the new owner succeeds and consumes that final slot. |

The matrix supplements, rather than replaces, the existing 1.4 single-session
regression suite. All current single-session behavior that remains in scope
must continue to pass when exactly one active Session exists.

## Q. Explicitly out of scope

v1.5 does not include:

- prompt, message, response, or transcript capture;
- terminal command-output capture;
- source-code capture for Developer-Tool tracking;
- cloud sync;
- cross-device active-session coordination;
- telemetry or product analytics;
- AI interpretation of concurrent work;
- new Developer-Tool providers such as Cursor, Windsurf, or Claude Code unless
  separately scoped;
- a complete redesign of application-triggered concurrency;
- process or window spying; or
- guaranteed attribution of repository-wide Git mutations to individual
  overlapping Threads.

This specification also does not authorize changes to production code,
schemas, UI, CLI, scripts, or tests by itself. Those changes belong to a later
implementation branch and must be reviewed against this contract.
